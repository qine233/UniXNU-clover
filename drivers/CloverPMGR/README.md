# CloverPMGR — publishing an `ApplePMGRNub` for an unchanged AMFI

round82's panel was the first panic screen this board ever drew, and it said
`"AMFI: No PMGR?"` (`ConfigurationSettings.cpp:235`, on a thread-call worker). Nothing about
AMFI changed between round81 and round82: what changed is that the kernel got a clock. AMFI
calls

```
IOService::waitForMatchingService (IOService::serviceMatching ("ApplePMGRNub"), timeout)
```

and that `timeout` is in **nanoseconds** — `iokit/Kernel/IOService.cpp:6582` turns it into an
absolute deadline with `clock_absolutetime_interval_to_deadline ()` and sleeps with
`SLEEPNOTIFYTO`. With no timer interrupt ever reaching EL1 (rounds 70–81) the deadline could
not expire, the call hung, and the boot still walked on to EL0. With the INTID fixed (round82)
it expires immediately, the match returns nothing, and AMFI panics. The clock made an old wall
visible; it did not build it.

This driver removes the wall. It publishes a service that AMFI's own discovery path matches,
without modifying a single byte of AMFI.

## What AMFI needs, and where it was checked

From the base repository's `scripts/audit-amfi-pmgr-contract.py`, re-run against our own
`out/clover/kernel/kernel.macho` (see `scripts/build-clover-pmgr.py`, which refuses to build if
any of it differs):

| step | address | the bytes there |
| --- | --- | --- |
| matching string | `0xfffffff0042dde02` | `ApplePMGRNub\0` |
| AMFI's call site | `0xfffffff004aaeb40` | `bl …; orr w15…; mov x0, x20; mov x1, x21; bl …` |
| dispatch import (read) | `0xfffffff005cfac08` | → `0xfffffff004a24adc` |
| dispatch import (write) | `0xfffffff005cfac10` | → `0xfffffff004a230ec` |
| original provider vptr | `0xfffffff005ce26d8` | slot 320 `0xfffffff004a20fbc` = `mov w0, #-1; ret`, slot 321 `0xfffffff004a20fc4` = `ret` |

So the contract is: take the matched nub, read its provider at `nub + 0x88`, call virtual slot
320, `OR` the low 32 bits with `4`, hand the result to slot 321. On Apple silicon that is
literally "the always-on domain reads as all-ones and the write does nothing". It is a
*service* requirement, not a power requirement.

## The shape

`CloverPlatformPower` derives from a **reconstructed** `ApplePMGR` (the header and the guarded
slot list are generated by `scripts/build-clover-pmgr.py` from the audited class size 0x4b8a8
and 340 virtual slots). Every slot except the AON pair is overridden to `panic()`, so a code
path that genuinely wants a clock, a rail or a secondary core speaks up instead of quietly
getting a stub. The nub itself is the original `ApplePMGRNub`, minted by the original factory at
`0xfffffff004a22568`.

`sheng_pmgr_run()` is the name the base repository's patch gives the hook in
`bsd/kern/bsd_init.c` (after `bsd_bufferinit ()`, before `IOKitInitializeTime ()`); it is not a
choice. The order it follows is the one UniXNU-sheng uses for the same structural problem:
load `com.apple.driver.ApplePMGR`, check the two classes by name and size, register our
metaclass with `preModLoad` / `__GLOBAL__sub_I_CloverPMGR.cpp` / `postModLoad`, allocate,
attach and `registerService (kIOServiceSynchronous)`, then prove the publication by running
AMFI's own query with a 2 s deadline.

**Every failure path here panics.** That is the one deliberate difference from sheng, whose
instrument returns quietly when a step does not hold. A silent bail photographs exactly like
round82's `AMFI: No PMGR?`, and on a board whose only output is the panel the two would be
indistinguishable.

## Boot argument

| value | behaviour |
| --- | --- |
| absent, or `0` | returns without touching anything (the kernel still links the provider) |
| `2` | publish and self-verify — what `board.toml` passes |
| anything else | `panic("CloverPMGR: failed at stage 1 …")` |

## Reading the result

`clover_pmgr_observation[16]` is drawn by the panic screen (`scripts/xnu-panic-screen.c`):

```
pmgr=<stage> status=<0 = ok> mode=<boot arg>
nub=<ptr> attached=<1> registered=<1>
aon=<read before>=>  <read after>
```

`stage` is the step it reached (`1` after the mode check, `2` after the nub was created, `3`
before exercising the AON pair, `5` after registration; `0x100 + slot` means a guarded power
slot was actually called). `status` is `0` only when AMFI's own `waitForMatchingService`
returned this very nub. The full slot map is in `CloverPMGR.cpp` next to the array.

## What this is not

No PMGR hardware exists on SDM660 in the sense XNU means it, no register map is claimed, and no
secondary CPU is enabled by anything here. `unimplemented (slot)` is the honest answer for
every power operation but the always-on pair, and it is loud on purpose.
## How this driver meets the UniXNU driver documentation

This is the clover driver that is closest to the documented shape, because it is a real IOService
subclass: `class CloverPlatformPower : public ApplePMGR` is the class shape of
`docs/drivers/xnu-drivers.md:19-64`, and the stages it runs — match, `start()`, publish by
`registerService()`, the nub it hands AMFI — are the runtime table at `docs/drivers/xnu-drivers.md:219-228`.
The `registerService()` calls are the last thing `start()` does, which is the order `:19-64` asks for, and
the service it publishes is the one AMFI already looks for by class name.

Layer and archive wiring follow `docs/drivers/overview.md:11-16` and
`docs/drivers/xnu-drivers.md:118-124` — `build-clover-pmgr.py` in `[kernel] archives`,
`CONFIG_XNU_SHENG_PMGR=y` in `configs/clover_defconfig`. The documented five-field object ABI of
`:106-116` is checked by that builder itself: it requires filetype `1` and build version `(2, 0x110000)`
(`build-clover-pmgr.py:150,152`), and the magic/CPU/subtype triple is refused earlier by the shared
`kits/NativePrelink/native_prelink.py`. It is *not* a loadable kext and that is deliberate: the original
`ApplePMGR` is a prelink root (`board.toml:92`) whose class this driver subclasses in the kernel, and
`docs/drivers/kexts.md:117` is the reason a staged kext is not an option on this path — recorded in the
source's own DOCUMENTED CONTRACT block.

No personality, hence no `Info.plist`: `docs/drivers/xnu-drivers.md:14` makes the plist the record of a
personality, and this driver has none — AMFI reaches it through its own
`IOService::serviceMatching("ApplePMGRNub")`, not through `iokit/KernelConfigTables.cpp`. The chain of
`extern "C"` entry points that replaced personalities for the other instruments, and the three concrete
prerequisites for changing that, are `notes/unixnu-doc-conformance.md` §5. Against the five test rows of
`docs/drivers/xnu-drivers.md:230-239` the gap is the third: the metaclass/`static_assert` arithmetic here
has no host model, unlike `drivers/CloverPower/PowerArb.h` and `drivers/CloverDsp/DspCore.h`, and it is
listed as an open item in §7.
